Context Processing Engine and Progressive DisclosureA core point of degradation in autonomous coding systems is context window bloat, where broad coding guidelines, architectural documentation, schemas, and test histories are aggressively loaded into the primary prompt. This pattern dilutes instruction attention, exhausts rate limits, and triggers cognitive drift. Antigravity resolves this through a bifurcated context architecture that balances permanent system governance with on-demand retrieval.Permanent system governance is maintained via global rules located at ~/.gemini/GEMINI.md and repository rules designated as Always On within .agents/rules/. These files are parsed on session startup and injected into the root context of every turn. Conversely, procedural domain knowledge is managed through progressive disclosure within the Agent Skills engine. Rather than parsing full instructional texts into memory, Antigravity extracts only the YAML frontmatter—specifically the name and description—of each skill residing in .agents/skills/<skill-name>/SKILL.md. The agent searches these descriptions during reasoning; only when a user task explicitly aligns with a skill's declared purpose does the platform read the complete Markdown body and associated operational scripts into the active context window.Context boundaries are strictly isolated during subagent delegation. In Antigravity, subagents spawned to conduct repository sweeps or execute builds do not inherit the conversational trajectory or accumulated token debris of the parent session. Each subagent launches with an independent context window initialized with the workspace path, assigned system instructions, and targeted task arguments, preventing cross-turn context pollution.Configuration Scopes and Precedence HierarchyAntigravity enforces a four-tiered configuration precedence hierarchy that governs tool permissions, model selections, and command sandboxing across all interaction surfaces:Configuration LayerFile / Mechanism LocationEvaluation PrecedencePrimary Governance ScopeCLI & Turn OverridesInteractive flags (--sandbox, --model, @mention)Level 1 (Highest)Overrides model routing, activates manual rules, and forces sandbox states per session.Custom Agent Profile.agents/agents/<name>.md or ~/.gemini/config/agents/[cite: 17, 18]Level 2Defines role-specific tool allowlists, reasoning tiers, and execution policies (auto, sandbox).Workspace / Project.agents/rules/, .agents/skills/, .agents/hooks.json[cite: 14, 15, 19]Level 3Governs project-level coding standards, directory-scoped rules, and CI validation hooks.Global Environment~/.gemini/GEMINI.md, ~/.gemini/antigravity-cli/settings.json[cite: 9, 15, 16]Level 4 (Lowest)Establishes developer workstation defaults, universal security denylists, and user profiles.When permissions conflict across these tiers, Antigravity evaluates rules in strict order: Deny rules take precedence over Ask rules, which in turn take precedence over Allow rules. The terminal sandbox avoids virtual machine overhead by utilizing native kernel containment mechanisms:Linux Namespaces: Creates unprivileged execution environments that isolate mount points, obscure host process tables, configure loopback network namespaces, and restrict resource limits.macOS Seatbelt Profiles: Executes processes within sandboxed containment using the sandbox-exec kernel framework and custom Scheme-based Security Profiles (SBPL), restricting disk writes exclusively to project directories and designated cache locations.Sandbox boundaries dynamically synchronize with configured agent permissions. Paths authorized under read_file populate the sandbox's read-only filesystem allowlist, while paths declared under write_file populate the read-write allowlist. Crucially, sensitive host locations—including ~/.ssh, ~/.gnupg, and local .env secret files—are explicitly blocked from being mounted inside the sandbox. Terminal network egress is denied by default; outbound HTTP/TCP requests are blocked unless domains are explicitly granted in the read_url policy configuration. import os
import sys
import json

def analyze_directory(root_dir, max_depth=2):
    result = {"root": root_dir, "directories": [], "manifests": []}
    known_manifests = {
        "package.json", "pyproject.toml", "Cargo.toml", 
        "go.mod", "pom.xml", "build.gradle", "GEMINI.md"
    }
    
    root_dir = os.path.abspath(root_dir)
    base_depth = root_dir.rstrip(os.path.sep).count(os.path.sep)
    
    for current_root, dirs, files in os.walk(root_dir):
        # Exclude common noisy directories
        dirs[:] = [d for d in dirs if d not in {
            ".git", "node_modules", ".venv", "__pycache__", 
            "dist", "build", "target", ".next"
        }]
        
        current_depth = current_root.count(os.path.sep) - base_depth
        if current_depth <= max_depth:
            rel_path = os.path.relpath(current_root, root_dir)
            if rel_path != ".":
                result["directories"].append(rel_path)
            
            for file in files:
                if file in known_manifests:
                    result["manifests"].append(os.path.join(rel_path, file))
                    
    return result

if __name__ == "__main__":
    target = sys.argv[1] if len(sys.argv) > 1 else "."
    data = analyze_directory(target)
    print(json.dumps(data, indent=2))
